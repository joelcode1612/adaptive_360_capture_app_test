# 2026-11-14

## 38-target sphere: fixed the world-up frame bug (root cause of "targets scattered/tilted")

**Root cause.** `levelStartFrame` levelled against `+Y` up and built the frame
with `Quat.fromYawPitch`, but Android's `TYPE_ROTATION_VECTOR` reports an
**East–North–Up** frame where up is `+Z` and `+Y` is magnetic north. The
"horizontal projection" was therefore onto the East–Up plane and the "yaw" was
a rotation about the north axis — a *roll*. Measured on a phone 30° down facing
north, target 1's world direction came out `(0,0,−1)` (straight at the floor),
60° off the reticle instead of 30° above it.

**Fix.** `levelStartFrame` / `hasStableHeading` now take an explicit `worldUp`
and build the levelled device→world rotation from an orthonormal basis
`[right | up | −heading]` via `Quat.fromMatrix3` (det +1, never a mirror).
`RotationSource.worldUp` declares the frame: default `+Y` (synthetic/test),
`NativeRotationSource` returns `kAndroidSensorWorldUp = (0,0,1)`.

**Also changed**
- `_recomputeGuide` now writes `_activeTargetId`/error/turn/pitch atomically, so
  the arrow, pill, ring and shutter can never describe different targets.
- Guidance is turn-by-turn: "Turn right 30° to target 2." (`guideTurnDeg`,
  `guidePitchDeg`, `guideBehind` are signed camera-frame bearings).
- Reticle: opaque white plate → transparent-interior ring whose radius **is**
  the 5° cone; active marker drawn above it; non-active markers never green.
- Progress map: shape-coded states + ring-coloured dots + live look dot +
  sampled ring outlines; palette now distinguishes upper (green) from lower
  (orange) — they were both `#6FB3E0`.
- `readJpegSize` applies EXIF orientation, so `sourceImageHeight` matches what
  `imread` decodes (the stitcher derives its focal from it).
- Split pure rotation maths into `domain/sphere_math.dart` (no `dart:ui`);
  `sphere_projection.dart` re-exports it.

**Route stays id-order** (middle → zenith → upper → lower → nadir). Proof it is
optimal for max step: a pole is 90° from every non-pole target, so ≥90° is
unavoidable; this order pays exactly two 90° steps and nothing above.

## Verification tooling (important)

`flutter test` and `dart run` both fail on this host — the `opencv_dart` build
hook runs CMake/`rc` and the sandbox blacklists `reg.exe`. Workaround:

```
dart --packages=.dart_tool/sphere_verify_package_config.json \
     tool/verify_sphere_geometry.dart
```

with a one-package config (`adaptive_360_capture_app` only) so no native hook
runs. 38 geometry checks pass. `flutter analyze` clean; debug APK builds.
No device attached, so nothing physical was verified.
